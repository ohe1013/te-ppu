# PvE 낙하 블록 대전 비공개 프로토타입 설계

- 작성일: 2026-08-02
- 상태: 사용자 승인 완료
- 대상: Apps-in-Toss를 최종 배포 대상으로 하는 3층 PvE 프로토타입

## 1. 목적과 출시 경계

이 프로젝트의 첫 결과물은 낙하 블록 줄 삭제와 개별 방해 칸 공격을 결합한 전투가 재미있는지 검증하는 비공개 프로토타입이다. 플레이어는 동시에 게임을 진행하는 AI를 쓰러뜨리고 3층 탑을 올라 구조 대상에게 도달한다.

프로토타입은 익숙한 낙하 블록 규칙과 `뿌요뿌요 통`식 예고·상쇄 흐름을 가까이 재현한다. 따라서 이 빌드는 Apps-in-Toss 공개 출시 후보가 아니다. 공개 제출 전에 별도 독자화 설계와 게임 IP 경험이 있는 전문가의 검토를 거쳐 필드, 조각, 회전, UI, 공격 연출, 명칭, 그래픽, 사운드를 독자적으로 재설계해야 한다.

프로토타입에서도 Tetris, Puyo Puyo, SEGA의 명칭·로고·캐릭터·음악·그래픽·고유 용어와 공식 자산은 사용하지 않는다. 임시 자산은 자체 제작한 기하학 도형과 무상 사용 권리가 확인된 소리만 사용한다.

## 2. 완료 기준

프로토타입은 다음 조건을 모두 만족할 때 완료로 본다.

- 세로 화면에서 플레이어와 AI의 동일 크기 `10×20` 필드가 동시에 보인다.
- 기본 낙하 블록 배치, 줄 삭제, 콤보 공격, 공격 예고·상쇄·반송과 개별 방해 칸 낙하가 동작한다.
- 세 아이템이 15% 규칙에 따라 등장하고 플레이어와 AI가 동일한 조건으로 획득·사용한다.
- 속도와 판단력이 서로 다른 AI 세 층을 순서대로 플레이할 수 있다.
- 승리한 층의 다음 층이 해금되고 최고 해금 층과 설정이 저장된다.
- 같은 난수 시드와 같은 명령 열은 같은 최종 상태와 이벤트 열을 만든다.
- 모바일 터치 조이스틱과 회전 버튼으로 안정적으로 조작할 수 있다.
- 브라우저 프로토타입과 Apps-in-Toss 샌드박스에서 핵심 흐름을 검증할 수 있다.

## 3. 범위 밖

첫 프로토타입에는 다음을 포함하지 않는다.

- 사용자 간 실시간 대전과 대전 서버
- 랭킹, 소셜, 길드, 친구 초대
- 광고, 인앱 결제, 유료 아이템
- 전투 중간 상태 저장과 복원
- 일반 홀드 기능
- 가로 화면과 사용자 지정 키 배치
- 최종 캐릭터, 배경, 음악과 공개 출시용 브랜딩
- 게임 등급 심의 신청과 Apps-in-Toss 공개 출시

## 4. 기술 선택

### 4.1 구성

- TypeScript: 결정론 게임 코어와 AI
- React: 앱 화면, 메뉴, 조작부, 아이템, 설정
- PixiJS의 WebGL 렌더러: 필드, 블록, 캐릭터, 파티클과 전투 애니메이션
- Vite: CSR 정적 번들
- `@apps-in-toss/web-framework`: 플랫폼 생명주기와 출시 단계 연동

WebGPU는 사용하지 않고 모바일 WebView 호환성이 높은 WebGL을 사용한다. 서버 사이드 렌더링과 `eval`은 사용하지 않는다.

### 4.2 모듈 경계

```text
src/
  core/       순수 TypeScript 규칙, 상태, 명령, 이벤트, 난수
  ai/         난이도 프로필과 명령 생성
  render/     PixiJS 장면, 스프라이트, 애니메이션, 사운드 신호
  ui/         React 화면, 아이템, 조이스틱, 설정
  platform/   저장소와 Apps-in-Toss 어댑터
  app/        화면 전환과 의존성 조립
```

`core`는 DOM, React, PixiJS, Apps-in-Toss SDK를 가져오지 않는다. 화면 입력과 AI는 같은 `GameCommand` 인터페이스를 통해서만 코어를 조작한다. 렌더러는 코어가 배출한 상태와 이벤트를 표현하며 판정 결과를 결정하지 않는다.

### 4.3 데이터 흐름

```text
터치 조작 ─┐
           ├─> MatchCoordinator ─> 결정론 상태 + GameEvent[]
AI 판단 ───┘          │                        │
                      │                        ├─> PixiJS 애니메이션
                      │                        ├─> React HUD
                      │                        └─> 사운드·햅틱
                      └─> ProgressRepository
```

게임 코어는 60Hz 고정 스텝으로 전진한다. 렌더링 프레임이 늦어져도 판정 스텝은 순서를 유지하고, 렌더러는 필요한 경우 상태 사이를 보간한다.

### 4.4 검토한 대안

- PixiJS 장면 안에 규칙을 함께 넣는 방식은 초기 화면 제작은 빠르지만 판정과 애니메이션이 결합되어 결정론 테스트, AI, 리플레이와 향후 네트워크 대전에 불리하므로 채택하지 않았다.
- Phaser 같은 완성형 엔진은 장면·입력·트윈 기능을 제공하지만 이 격자 게임에 필요하지 않은 계층이 늘고 React 및 Apps-in-Toss 연동 경계가 복잡해져 채택하지 않았다.
- 별도 게임 코어와 표현 계층을 분리하는 현재 구조는 초기 파일 수가 늘어나는 대신 테스트, 디자인 교체와 향후 서버 재사용에 가장 유리해 채택했다.

## 5. 경기 상태와 난수

### 5.1 필드와 조각

- 필드는 10열, 보이는 20행과 스폰 판정용 숨은 4행으로 구성한다.
- 7종 네 칸 조각과 7-bag 생성기를 사용한다.
- 회전은 벽차기를 포함한 SRS 방식으로 처리한다.
- 다음 조각 두 개와 고스트 위치를 표시한다.
- 일반 홀드는 제공하지 않는다. 다음 두 조각 교환은 아이템의 전용 효과다.
- 초기 중력은 800ms마다 한 칸, 소프트 드롭은 50ms마다 한 칸이다.
- 바닥 접촉 후 고정 유예 시간은 500ms이며, 이동·회전으로 최대 15회까지 갱신할 수 있다.
- 새 조각의 스폰 위치가 막히거나 방해 칸이 숨은 행을 넘어가면 패배한다.

### 5.2 결정론 난수

경기 시작 시 하나의 `matchSeed`를 만든다. 여기서 다음 독립 스트림을 파생한다.

- 조각 bag 스트림
- 아이템 등장·종류·표식 칸 스트림
- 플레이어에게 떨어질 방해 칸 열 스트림
- AI에게 떨어질 방해 칸 열 스트림
- AI 실수 선택 스트림

플레이어와 AI의 n번째 조각 및 아이템 후보는 같은 순서를 사용한다. 방해 칸과 AI 실수는 별도 스트림을 사용해 한 시스템의 난수 소비가 다른 시스템의 결과를 바꾸지 않게 한다.

## 6. 경기 흐름

플레이어와 AI는 다음 상태 기계를 각자 독립적으로 반복한다. `MatchCoordinator`는 같은 60Hz 틱에서 두 상태 기계를 전진시키고 양쪽 사이의 아이템·공격 효과를 조정한다.

```text
COUNTDOWN
  -> SPAWN
  -> ACTIVE
  -> LOCK
  -> CLEAR_AND_ATTACK
  -> OFFSET
  -> GARBAGE_DROP
  -> TOP_OUT_CHECK
  -> SPAWN
```

- `ACTIVE`: 이동, 회전, 소프트 드롭, 하드 드롭과 사용 가능한 즉시 아이템을 처리한다.
- `LOCK`: 조각의 네 칸과 아이템 표식을 필드 셀로 확정한다.
- `CLEAR_AND_ATTACK`: 완성 줄을 삭제하고 콤보와 공격량을 계산한다.
- `OFFSET`: 받을 공격과 보낼 공격을 1:1로 상쇄하고 초과분을 상대 대기열로 보낸다.
- `GARBAGE_DROP`: 남은 받을 공격을 다음 조각 스폰 전에 하나씩 떨어뜨린다.
- 동일 틱에 양쪽 공격이 발생하면 양쪽의 기존 대기열 상쇄를 먼저 계산한 뒤 초과분끼리 순수 차이를 계산해 한쪽에만 추가한다.
- 동일 틱에 양쪽이 모두 톱아웃하면 무승부로 처리하고 층을 해금하지 않은 채 재경기를 제안한다.

한 틱 안의 처리 순서는 다음과 같이 고정한다.

1. 플레이어와 AI 명령을 수집한다.
2. 양쪽의 시간 멈춤 명령을 동시에 적용한다. 같은 틱에 서로 사용하면 양쪽 모두 정지한다.
3. 정지되지 않은 각 필드의 이동·중력·고정·아이템 명령을 처리한다.
4. 양쪽 줄 삭제와 공격량을 계산한 뒤 상쇄와 반송을 동시에 확정한다.
5. 방해 낙하와 톱아웃을 처리하고 이벤트를 배출한다.

## 7. 줄 삭제, 콤보와 공격

### 7.1 콤보 정의

콤보는 연속해서 줄을 삭제한 조각 배치 횟수다.

```text
normalAttack = clearedLineCount + max(0, comboIndex - 1)
```

- 처음 줄을 지운 배치는 1콤보다.
- 다음 조각도 한 줄 이상 지우면 2콤보가 된다.
- 한 번에 여러 줄을 지워도 콤보는 한 단계만 증가한다.
- 줄을 지우지 못한 일반 조각이 고정되면 콤보는 0으로 초기화된다.
- 콤보 보너스에는 상한을 두지 않는다.
- 예: 2콤보째 4줄 삭제는 `4 + 1 = 5`, 3콤보째 4줄 삭제는 `4 + 2 = 6`칸을 공격한다.

### 7.2 예고와 상쇄

- 수신 공격은 필드 위 예고 UI와 숫자로 표시한다.
- 자신의 공격은 먼저 자기 수신 대기열을 1:1로 줄인다.
- 수신량보다 공격량이 많으면 남은 수량만 상대에게 전송한다.
- 상쇄하지 못한 공격은 현재 조각의 모든 삭제·공격 판정이 끝난 뒤 떨어진다.
- 공격 낙하는 이미 조작 중인 조각을 방해하지 않는다.

### 7.3 방해 칸 낙하

- 각 방해 칸은 수신자 전용 시드 난수로 0~9열을 독립 선택한다. 같은 열을 연속 선택할 수 있다.
- 한 칸씩 필드 위에서 떨어져 해당 열의 기존 더미 바로 위에 고정된다.
- 방해 칸은 일반 고정 셀처럼 줄의 일부가 될 수 있고 완성 줄과 함께 삭제된다.
- 방해 낙하 자체는 줄 삭제 판정을 실행하지 않는다. 방해 낙하로 완성된 줄은 다음 일반 조각 고정 때 다른 완성 줄과 함께 삭제된다.
- 한 줄 삭제 아이템은 선택한 한 행만 제거하므로, 다른 완성 줄을 추가로 검사하거나 삭제하지 않는다.
- 프로토타입에서는 한 번에 떨어지는 수량에 상한을 두지 않고 상쇄 후 남은 대기열 전체를 한 번의 `GARBAGE_DROP`에서 처리한다.
- 방해 낙하가 숨은 4행을 넘거나 다음 조각 스폰을 막으면 수신자가 패배한다.

## 8. 아이템

### 8.1 등장과 획득

- 각 새 조각을 만들 때 아직 등장하지 않은 아이템이 있으면 정확히 한 번 15% 확률 판정을 한다.
- 성공하면 남은 종류 중 하나와 조각의 네 칸 중 하나를 균등하게 선택한다.
- 선택된 칸에는 회전과 이동을 따라가는 아이템 표식을 붙인다.
- 종류별로 한 경기에서 최대 한 번만 등장한다.
- 등장한 즉시 해당 종류를 등장 완료로 기록한다. 표식 칸을 지우지 못해도 재등장하지 않는다.
- 표식 셀이 포함된 줄이 삭제되는 순간, 셀을 제거하기 전에 해당 아이템을 획득한다.
- 한 번에 여러 표식 줄을 지우면 해당 아이템을 모두 획득한다.
- 플레이어와 AI 모두 같은 등장·획득 규칙을 따른다.

### 8.2 한 줄 삭제

- 아이템 버튼을 누르면 행 선택 모드로 진입한다. 이 시점에는 아이템을 소비하지 않는다.
- 블록이 하나 이상 있는 보이는 행만 유효한 대상이다. 빈 행 터치는 무시한다.
- 유효 행을 누르면 아이템을 소비하고 행 전체를 삭제한 뒤 위 행을 한 칸씩 내린다.
- 해당 행의 아이템 표식은 삭제 전에 획득한다.
- 정확히 1칸 공격을 만들며 일반 공격처럼 수신 대기열을 먼저 상쇄한다.
- 일반 콤보를 증가시키거나 초기화하지 않는다.
- 행 선택 모드에는 취소 버튼과 현재 대상 행 강조를 제공한다.
- 행 삭제와 위 행 하강 후 현재 조작 중인 조각이 고정 셀과 겹치면, 조각을 유효해질 때까지 필요한 최소 행만큼 위로 이동한다. 숨은 행 안에서도 유효 위치를 만들 수 없으면 톱아웃으로 처리한다.

### 8.3 시간 멈춤

- 버튼 입력을 코어가 수신한 틱부터 상대를 180틱, 즉 게임 시간 3초 동안 정지한다.
- 상대의 입력, AI 판단, 중력, 고정 유예, 아이템 타이머와 방해 낙하가 멈춘다.
- 정지당한 필드 위에 남은 시간을 표시한다. 렌더링과 UI는 계속 동작한다.
- 사용자의 필드와 게임은 계속 진행한다.
- 앱이 백그라운드로 가면 전체 경기 시간이 멈추므로 정지 시간도 소모되지 않는다.

### 8.4 다음 조각 스위치

- 아이템 하나를 획득하면 3회 충전을 부여한다.
- 한 번 사용할 때 현재 조각은 유지하고 다음 조각과 그다음 조각의 순서만 맞바꾼다.
- 사용 시마다 충전을 하나 차감하고 HUD에 남은 횟수를 표시한다.
- `ACTIVE` 상태에서만 사용할 수 있다.

## 9. AI와 3층 난이도

AI는 가능한 회전·열·낙하 위치를 열거하고 필드 높이, 구멍, 울퉁불퉁함, 완성 줄, 콤보 지속 가능성, 수신 공격과 아이템 가치를 점수화한다. 목표 배치를 정한 뒤에도 조각을 순간 이동시키지 않고 플레이어와 같은 이동·회전·낙하 명령을 순서대로 보낸다.

초기 난이도 프로필은 다음과 같다.

| 층 | 반응 간격 | 탐색 | 실수 모델 | 아이템 사용 |
|---|---:|---|---|---|
| 1층 | 800ms | 현재 조각만 | 상위 5개 후보 중 무작위 | 획득 후 첫 유효 시점에 단순 사용 |
| 2층 | 450ms | 현재+다음 1개 | 상위 3개 후보 중 가중 선택 | 위험도와 빈 공간 기준 휴리스틱 |
| 3층 | 200ms | 현재+다음 2개 | 최고 후보 선택 | 콤보·상쇄·플레이어 높이를 함께 판단 |

- AI는 화면에 공개된 현재 조각과 다음 두 조각만 안다.
- 플레이어의 미래 조각, 미래 아이템 난수와 방해 칸 열은 알 수 없다.
- 모든 층에서 AI도 아이템 표식 셀을 실제로 줄 삭제해야 아이템을 획득한다.
- 반응 간격과 평가 가중치는 설정 데이터로 분리하되 위 값이 프로토타입의 초기값이다.

## 10. 탑 진행과 저장

- 새 사용자는 1층만 선택할 수 있다.
- 1층 승리 시 2층, 2층 승리 시 3층을 영구 해금한다.
- 패배하면 현재 층을 다시 시작할 수 있다.
- 각 층 시작 시 양쪽 필드, 공격 대기열, 콤보, 아이템 등장 기록과 인벤토리를 초기화한다.
- 3층 승리 시 구조 장면과 프로토타입 엔딩을 보여준다.
- 클리어한 층은 다시 플레이할 수 있다.
- 저장 항목은 `schemaVersion`, 최고 해금 층, 층별 클리어 기록, 사운드·햅틱 설정이다.
- 전투 도중 상태는 저장하지 않는다. 전투 중 종료하면 선택한 층의 시작 화면으로 돌아온다.

`ProgressRepository` 인터페이스 뒤에 저장을 둔다. 비공개 프로토타입은 브라우저 로컬 저장소를 사용한다. 공개 출시 단계에서는 게임 사용자 식별키와 서버 저장소를 사용하는 구현으로 교체해 기기 변경 후에도 진행을 복원한다.

## 11. 화면과 조작

### 11.1 화면 구성

세로 화면 전용이며 두 필드를 같은 크기로 좌우 배치한다. AI 필드는 미니맵으로 축소하지 않는다.

```text
┌──────── 층·설정·닫기·공격 예고 ────────┐
│ 플레이어 상태          │          AI 상태 │
│ 다음 조각·콤보         │ 다음 조각·콤보   │
├──────────────┬──────────────┤
│   플레이어   │      AI      │
│    10×20     │    10×20     │
│              │              │
├──────────────┴──────────────┤
│  한줄삭제 │ 정지 │ 스위치와 남은 충전    │
│     원형 조이스틱       원형 회전 버튼     │
└─────────────────────────────┘
```

AI 화면에는 조각 이동·회전·낙하, 아이템 표식, 다음 두 조각, 콤보, 줄 삭제, 공격 예고·상쇄, 아이템 획득·사용과 정지 시간을 모두 실시간으로 표시한다.

한 줄 삭제 행 선택 중에는 손가락 위치와 가장 가까운 플레이어 행을 강조하고, 같은 행에서 손을 떼면 확정한다. 손가락을 위아래로 움직여 대상 행을 바꿀 수 있으며 필드 밖에서 놓으면 취소한다.

### 11.2 원형 조이스틱

- 왼쪽 아래에 고정 원형 베이스와 이동 손잡이를 둔다.
- 포인터가 반지름의 20% 이내에 있으면 중립이다.
- 좌우 임계값을 넘는 순간 한 칸 이동하고, 160ms 유지 후 50ms마다 반복 이동한다.
- 아래 임계값을 유지하면 50ms마다 한 칸 소프트 드롭한다.
- 위 방향이 지배축이고 반지름의 80%를 처음 넘을 때 하드 드롭을 정확히 한 번 실행한다.
- 하드 드롭은 중립 구역으로 돌아오거나 손을 뗀 뒤에만 다시 준비된다.
- 대각선 입력은 절대 이동량이 큰 축 하나만 선택한다. 같은 값이면 수평을 우선해 우발적 하드 드롭을 막는다.
- `pointerup`, `pointercancel`, 포인터 캡처 상실과 앱 비활성화 시 모든 연속 입력을 즉시 해제한다.
- 마우스와 터치에 동일한 Pointer Events 경로를 사용한다.

오른쪽 아래 원형 버튼은 누를 때마다 시계 방향으로 한 번 회전한다. 길게 눌러도 반복 회전하지 않는다.

### 11.3 화면 전환

```text
BOOT -> TITLE/TOWER -> FLOOR_INTRO -> MATCH
  -> RESULT_WIN/RESULT_LOSS -> TOWER 또는 ENDING
```

- 모든 화면은 Safe Area를 침범하지 않는다.
- 우측 상단에는 Apps-in-Toss 닫기 경로를 유지한다.
- 경기 중 닫기를 누르면 종료 확인 모달을 표시하고 확인 전까지 양쪽을 일시정지한다.
- 앱이 백그라운드로 가면 게임, AI, 아이템 시간과 사운드를 정지한다.
- 포그라운드 복귀 시 `3-2-1` 카운트다운 후 양쪽을 동시에 재개한다.

## 12. 표현 계층

PixiJS는 다음 이벤트를 애니메이션으로 표현한다.

- 조각 이동, 회전, 고스트, 착지
- 줄 삭제 섬광과 파티클
- 콤보 숫자와 캐릭터 반응
- 공격 칸이 상대에게 이동한 뒤 필드 위에서 개별 낙하
- 예고 공격 감소와 반송
- 아이템 표식 발광, 획득, 사용과 정지 오버레이
- 승리, 패배와 층 클리어

애니메이션이 끝나지 않아도 코어 판정을 되돌리지 않는다. 중요한 이벤트는 렌더러 큐에서 순서대로 표현하고, 프레임 저하 시 장식 파티클 수부터 줄인다. 그래픽 자산을 불러오지 못하면 기하학 기본 블록으로 경기를 시작할 수 있어야 한다.

## 13. 오류 처리

- 충돌 때문에 불가능한 이동·회전 명령은 상태를 바꾸지 않고 무시한다.
- `ACTIVE`가 아닌 상태에서 온 조작과 아이템 명령은 소비하지 않고 무시한다.
- 입력 컨트롤러는 `pointerup`, `pointercancel`, `lostpointercapture`, `window.blur`, `visibilitychange`와 컴포넌트 해제 시 공통 `resetAll()`을 호출해 고정된 연속 입력을 해제한다.
- 저장 데이터는 `schemaVersion`으로 검사한다. 파싱 실패 또는 지원하지 않는 버전이면 원본을 별도 백업 키에 보존하고 기본 진행으로 복구한 뒤 사용자에게 안내한다.
- 저장소 쓰기가 실패하면 현재 세션의 진행은 메모리에 유지하고 저장 실패와 재시도 방법을 안내한다.
- Apps-in-Toss SDK를 사용할 수 없는 일반 브라우저에서는 로컬 어댑터로 동작한다.
- 필수 그래픽 로딩 실패 시 기본 그래픽으로 계속하고, 사운드 실패는 무음으로 계속한다.
- 예기치 않은 코어 불변식 위반은 해당 경기의 시드와 명령 로그를 남기고 안전하게 결과 화면으로 이동한다.

## 14. 테스트 전략

### 14.1 코어 단위 테스트

- 7-bag, 이동, 회전, 벽차기, 충돌, 고정과 톱아웃
- 1~4줄 삭제와 행 하강
- 연속 삭제 콤보와 무삭제 고정 초기화
- 공격 공식의 예시 `4+1=5`, `4+2=6`
- 공격 예고, 1:1 상쇄, 초과분 반송과 동일 틱 양방향 처리
- 방해 칸의 시드 재현성, 중복 열과 톱아웃
- 아이템 15% 판정, 균등 종류·셀 선택과 종류별 1회 제한
- 표식 이동·고정·행 이동·획득
- 한 줄 삭제의 1공격, 콤보 비변경과 연쇄 아이템 획득
- 한 줄 삭제 후 활성 조각 충돌 시 최소 상향 이동과 톱아웃
- 시간 멈춤 180틱과 백그라운드 중 시간 비소모
- 다음 두 조각 교환과 3회 충전

### 14.2 속성·결정론 테스트

- 임의 시드와 명령 열에서 필드 셀이 겹치거나 경계를 벗어나지 않는다.
- 같은 시드와 명령 열의 상태 해시와 이벤트 열이 항상 같다.
- 서로 다른 난수 스트림의 소비가 조각 순서를 바꾸지 않는다.
- 100,000회의 등장 가능 조각 표본에서 아이템 등장률이 15%의 ±1%p 범위에 있고 각 경기에서 종류별 한 번을 넘지 않는다.

### 14.3 AI 시뮬레이션

- 각 층 수천 경기를 실행해 불법 명령, 무한 루프와 비정상 메모리 증가를 탐지한다.
- 동일한 기준 상대에 대해 1층보다 2층, 2층보다 3층의 승률이 높아야 한다.
- AI가 비공개 미래 상태를 읽지 않는지 의존성 테스트로 확인한다.
- AI가 획득하지 않은 아이템을 사용하거나 충전을 초과하지 않는지 검증한다.

### 14.4 UI와 실기기 테스트

- 조이스틱 중립 구역, 장기 누름, 대각선, 빠른 반전, 하드 드롭 재무장과 터치 취소
- 한 줄 삭제의 행 선택·취소와 좁은 화면의 행 스냅
- 최소 360×640부터 430×932까지 동일 크기 양쪽 필드 표시
- Safe Area, 닫기 확인, 백그라운드·복귀와 사운드 중지
- 평균 60fps를 목표로 하며 중급 모바일 기기에서 긴 경기 중 지속 프레임 저하와 메모리 증가가 없어야 한다.
- 최초 화면은 10초 안에 표시한다.
- Apps-in-Toss 샌드박스와 실제 토스앱 QR 테스트를 모두 수행한다.

## 15. Apps-in-Toss 공개 출시 전 필수 게이트

프로토타입 성공 후에도 다음 작업이 끝나기 전에는 공개 출시하지 않는다.

1. 독자화 설계: 필드·조각·회전·공격·UI·연출·명칭을 출시용으로 재설계
2. IP 검토: 최종 플레이 영상, 이름, 아이콘, 스크린샷, 음악과 자산 라이선스 검토
3. 저장 교체: 사용자 식별키에 연결된 서버 저장과 기기 변경 복원
4. 게임 등급 증빙 확보
5. Apps-in-Toss 게임 체크리스트와 실제 토스앱 QR 테스트 완료
6. 최종 앱 정보, 고객문의 채널, 로고와 썸네일 준비

플랫폼 검수 통과는 권리 비침해 판단이 아니다. 권리 신고가 접수되면 별도의 임시 미노출·소명 절차가 적용될 수 있다.
